# 노트북 성능 개선 — 2026-10-29

대상: 사용자가 알려 준 Ryzen 230 / RAM 16GB / Radeon 760M. 스테이지 4와 바르굴 보스전의 멈춤을 우선 줄였다. 사용자의 실제 플레이 브라우저에서 60FPS를 확인한 것은 아니다.

## 적용

- 기본 내부 해상도 960×540. 설정의 고화질은 화면 크기에 맞춰 최대 1920×1080. 이펙트 감소를 켜면 기본 해상도로 제한한다. 게임 좌표와 판정은 유지한다.
- JS에 포함된 이미지 68개를 `assets/runtime/`에 무손실 분리했다. 원본 바이트의 SHA-256 앞 24자리가 파일명이며 로컬 서버에서 장기 캐시한다. JS는 수정 사항을 재검증한다. 처음 받는 이미지의 총 바이트가 사라지는 것은 아니다.
- 배경·바닥은 필요할 때 로드하고 이미지 8개, 축소 타일 8개로 제한한다. 보스 시트는 해당 스테이지에 진입할 때 디코딩한다. 스테이지 그래픽 준비 중에는 안내를 표시하고 실제 게임 루프의 시간 진행을 멈춘다.
- 큰 시트를 처음 그릴 때 수백 ms가 걸리는 비용을 로딩 단계로 옮겼다. 현재 스테이지와 공통 병사 시트의 CPU 래스터를 준비하고, 화면에는 작은 프레임 캐시를 그린다. 이전 스테이지의 CPU 래스터는 해제한다. 프레임 96개, 이펙트 48개; 각 캔버스 캐시의 메모리 상한은 24MiB다. 큰 원본 시트를 유지하는 메모리는 별도이며 성능 표시 API에서 `sourceBytes`로 확인한다.
- 바르굴 근접 공격의 타임라인 검색을 WeakMap으로 재사용한다. 공격 타이밍, 충돌 범위, 피해량은 변경하지 않았다.
- 일시정지·설정 등 정지 화면은 바뀔 때만 그린다. 키·포인터·설정 변경·탭 복귀는 대기 타이머를 취소하고 바로 프레임을 요청한다.
- 설정의 **성능 표시 (FPS)**: 프레임 간격 p95, 연산·그리기 시간, 실제 내부 해상도를 표시한다. 측정 기록은 최근 180개로 제한한다. 콘솔에서 `BMK_PERF.snapshot()`으로 캐시 상태도 볼 수 있다.
- Streamlit 컴포넌트에는 이미지 매니페스트의 파일도 복사한다. 단일 HTML 내보내기는 이미지 데이터를 다시 포함하므로 큰 파일이 되는 기존 성질을 유지한다.

## 측정

`node tools/perf-stage4.cjs`는 사용자 브라우저와 분리된 임시 Chrome 프로필과 로컬 서버를 사용한다. 스테이지 4 병사 4명, 바르굴 1·2페이즈의 십자 빙결 반복을 각각 150번 업데이트·렌더링한다. 키 이동과 공격을 모두 사용하는 장시간 실전 벤치마크는 아니다. 첫 렌더링 비용도 포함한다. 개선 후에는 실제 게임과 같이 스테이지 준비를 기다리고 준비 시간은 따로 기록한다.

| 항목 | 변경 전 | 변경 후 독립 실행 |
|---|---:|---:|
| 초기 JS 응답 본문 | 196.1MiB | 7.6MiB |
| 초기 생성 Image의 RGBA 환산 합계 | 829.6MiB | 380.7MiB |
| 스테이지 4 그리기 평균 / 최대 | 5.38 / 544.4ms | 2.40 / 67.5ms |
| 바르굴 1페이즈 그리기 평균 / 최대 | 4.32 / 486.5ms | 1.44 / 34.8ms |
| 바르굴 2페이즈 그리기 평균 / 최대 | 1.55 / 90.1ms | 1.16 / 4.3ms |

개선 후 스테이지 4 첫 준비에는 약 1.8초가 걸렸다. 이 시간은 전투 중 첫 이미지 처리 비용을 앞당겨 수행한 것이다. 초기 Image 합계는 압축 파일 크기나 실제 프로세스 전체 메모리가 아닌 `naturalWidth × naturalHeight × 4` 환산값이다. CPU 래스터·캔버스·GPU 메모리는 별도다.

당시 독립 headless 실행은 **그리기를 전혀 하지 않는 rAF 대조군도 평균 33.34ms**였다. 아래 추가 진단에서 절전 모드에 따른 브라우저 갱신 제한을 확인했다. 위 표는 절전 제한이 걸려 있던 시점의 처리 시간 비교이며 60FPS 보증 수치가 아니다. 짧은 단일 실행 결과이며 최대 시간은 실행마다 변한다.

원자료: `artifacts/perf-stage4-before.json`, `artifacts/perf-stage4-isolated.json`. 일시정지 중 시뮬레이션 틱과 그리기 횟수 동결, 키보드 재개, 기본·고화질 제한, 저사양 설정, 캐시 상한 및 브라우저 예외 없음도 도구 안에서 검증한다.

## 30FPS 고정 추가 진단

사용자가 `python server.py` 로컬 실행에서도 30FPS가 지속된다고 보고하여 재확인했다. Windows 전원 상태를 읽었을 때 배터리 16%, AC 미연결, 시스템 절전 활성 상태였다. 게임 스크립트를 제거한 페이지와 빈 HTTP 페이지도 약 33.3ms 간격으로 갱신됐다.

사용자 브라우저·Windows 설정은 변경하지 않고, 별도의 임시 Chrome 프로필에서만 에너지 절약 설정을 꺼 비교했다.

- 기본 상태: 빈 페이지 약 30.73ms, 게임 로드 후 무부하 rAF 약 33.34ms.
- 에너지 절약 해제: 빈 페이지 약 16.93ms, 게임 로드 후 무부하 rAF 약 16.67ms.
- 실제 루프 약 2.2초 측정: 스테이지 4 일반 전투 56FPS / 프레임 간격 p95 17.3ms, 바르굴 2페이즈 십자 빙결 반복 56FPS / p95 17.6ms. 최초 그리기 비용을 포함한 짧은 구간으로, 장시간 평균 FPS는 아니다.
- 브라우저 예외 없음. 게임 루프에 30FPS 상한을 추가하거나 타이머로 강제 우회하지 않았다.

즉, 관측된 30FPS 고정은 게임 부하와 별개로 절전 상태에서 브라우저가 갱신 주기를 줄인 영향이었다. Chrome 에너지 절약이 requestAnimationFrame의 갱신 주기에도 영향을 준다는 [공식 설명](https://developer.chrome.com/blog/memory-and-energy-saver-mode)과 일치한다. 로컬 플레이에서는 충전 연결 상태와 Chrome 설정 → 성능 → 에너지 절약을 확인한다.

진단 재실행: `node tools/fps-diagnose.cjs`. 원자료: `artifacts/fps-variants.json`. 이 도구는 자신이 만든 임시 프로필에만 설정을 적용한다.

## 자산 재생성

검증 완료: `node tests/regression.cjs` 전체 통과(브라우저 예외 없음), `VARGUL_SUITE=1`의 14개 전투 타임라인 통과, `python -m unittest discover -s tests -p test_server_bundle.py` 7개 통과. 일반 회귀 테스트의 대시 공격·필살기 기대값은 기존 코드에 이미 반영되어 있던 대시 찌르기와 20×4+150 피해에 맞췄으며 전투 동작 코드는 이 작업에서 변경하지 않았다. 스테이지 4와 설정 화면 스크린샷도 확인했다.

기존 아트 생성 도구를 실행한 뒤 `node tools/externalize-art.cjs`를 실행한다. 새 데이터 URL을 원본 바이트 그대로 분리하고 매니페스트를 갱신하며, 생성된 배경·바닥 선언에 지연 로딩을 적용한다. `assets/runtime/`와 `data/runtime-assets.json`도 배포에 포함해야 한다. 매니페스트에서 빠진 옛 파일은 이 도구가 자동 삭제하지 않는다.
